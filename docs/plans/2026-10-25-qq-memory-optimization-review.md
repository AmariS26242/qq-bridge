## 1. 系统是什么

### 1.1 拓扑

```
QQ 客户端
   │  （OneBot 协议）
   ▼
qq-bridge（Node 常驻进程，本项目）
   │  （把一个"会话 key"映射到一个 DSH session）
   ▼
DSH（DeepSeek Harness：agent 运行时 + 模型网关）
   │
   ▼
deepseek-flash（1,048,576 token 上下文窗口）
```

- **一个 QQ 会话（私聊或群）= 一个 DSH 会话**，映射存在 `state/sessions.json`：
  `{"sessions":{"private:<uid>":"session-<uuid>"}}`。
- 机器人自称"小鲸鱼"，人格由角色卡驱动；不聊天时"潜水"，由定时唤醒 + 触发条件（被 @、关键词、提问、随机概率）叫醒。
- AI 的文本输出**不会**自动发到 QQ，必须调用工具（`qq_send_message` 等）显式发送。这保证它可以"醒来看一眼再决定不说话"。

### 1.2 一轮对话的生命周期

```
消息到达
  → 触发唤醒（reason: message / proactive / timeout / replyCheck ...）
  → buildWakePromptV2() 组装一条提示词（第 2.6 节给出完整拼装顺序）
  → deliverPrompt() 送进 DSH 会话；DSH 把「系统提示词 + 该会话全部历史 + 本次输入」整块发给模型
  → 模型输出：① 调用工具（发消息 / 等待 / 查档案 ...）→ 回到上一步，这是"第 2 步"
              ② 结束本轮，设置下次唤醒条件
```

关键事实（整个方案的根源）：

> **DSH 不在服务端保存跨轮对话状态。每一"步"都是一次完整的 LLM 请求，输入 = 系统提示词 + 该会话截至目前的全部历史 + 本次新增。**

一次唤醒如果模型调用了 3 次工具，就是 3 次请求，每次都重放同样体积的历史。对话越长，每一步越贵。

### 1.3 会话生命周期（关键代码，`src/bridge.js:9372`）

```js
async function ensureSession(key) {
  const policy = sessionPolicy(key);
  if (!isSessionAllowedInCurrentMode(key)) throw new Error(...);
  const existing = state.sessions[key];
  if (existing) {
    if (!isCurrentSession(key, existing)) {
      retireSession(key);                       // 产物代际不匹配：丢弃
    } else {
      const applied = await ensureChatModel(existing);
      if (applied === 'not-found') retireSession(key);   // DSH 侧会话已不存在
      else return existing;                     // ★ 正常路径：永远复用同一个 session
    }
  }
  ... // 新建会话
}
```

`retireSession()` 只在四种情况被调用：用户 `/reset`、控制台"清上下文"、模式/权限变更、DSH 侧会话丢失。**没有任何按轮数/时间/体积的自动轮换。**

## 2. 记忆的五层 + 两条补历史腿

| 层 | 载体 | 目的 | 注入方式 | 实测状态 |
|---|---|---|---|---|
| **L0 会话原文** | DSH session（磁盘快照 `session.v4.jsonl.zstd`） | 具体对话连贯性 | 全量重放（无裁剪） | **85 轮 / 2555 条记录 / 2.6M 字符** |
| **L1 短记忆** | `state/social-v2.json` | 正在聊的话题、想说没说的话、对人的即时印象 | 拼进唤醒提示词的 `memoryLine` | **空**（85 轮 0 次写入） |
| **L2 长档案** | `state/profiles.json` | 长期人设/关系：具体事例 + 证据 + 时间衰减 | 拼进 `profileLine`（≤3 人 / ≤900 字） | **在用：1 人 52 条** |
| **L3 摘要投喂** | `social.pendingSummaries`（内存） | AI 潜水期间群里发生了什么 | 一次性 "silent turn" 灌进同一会话 | 今日 0 次 |
| **L4 跨会话语义记忆** | 独立向量索引（`memory-index/`，bge-small-zh + SQLite） | 回忆"以前某次会话" | 模型主动调用 `memory_search` 工具 | 4 次/85 轮 |
| 补腿 A 掉线补拉 | `src/catch-up.mjs` | 重连后补回错过的消息 | 最多 5 会话 × 50 条，10s 总预算 | 正常 |
| 补腿 B 唤醒前预取 | `src/wake-history.mjs` | 补上"醒来前"的最近对话 | 12 条 / ≤1600 字 / 2.5s 超时 | 正常 |
| 日记 | `state/diary/*.json` | 一天一页的自我叙事 | **不进提示词**，只影响行为摘要 | 1 页 |

### 2.1 L1 短记忆的衰减参数（`src/memory-decay.mjs:21`）

```js
export const DEFAULT_DECAY_CFG = Object.freeze({
  halfLifeDays: 7,       // 权重半衰期
  pendingFloor: 0.35,    // 待办类记忆的权重下限
  foldThreshold: 0.15,   // 低于此权重且同类 ≥3 条 → 折叠成一行
  foldMinCount: 3,
  maxChars: 1200,        // 注入总字符预算
  expiredGraceHours: 24
});
```

三类结构与上限：`activeTopics` ≤20 条且 24h 未再提即删；`pendingThoughts` 默认 2h 过期；`memberImpressions` ≤50 人。写入完全依赖模型主动调用 `qq_memory_append`。

### 2.2 L2 长档案的规则（`src/profiles.js:28`）

```js
export const PROFILE_DEFAULTS = Object.freeze({
```

关键质量约束：只接受具体事例 —— 文本 6–160 字、必须带 ≤80 字 `evidence`、`looksLikeBareLabel()` 会拦掉"他很友善"这类空泛标签、`scrubSensitive()` 脱敏。抽取由**独立的"学习会话"**执行（工具集只含档案读写），不污染主对话。

### 2.3 L3 摘要投喂（`src/bridge.js:11439`）

AI 潜水/观望期间消息不丢弃，进 `pendingSummaries`（每会话 ≤60 条）。随后用一次 silent turn 灌进**同一个 DSH 会话**：

```
【群聊摘要】过去一段时间群里发生了这些（你未逐条参与）：
<若干行 sender：text>
【最近对话】
<最近 20 条>
你不需要回复，只需记住这些内容，后续聊天会更自然。
```

silent 名额 5 分钟未消费即作废（`SILENT_TURN_TIMEOUT_MS = 300000`）。这是"潜水也知道群里发生了什么"的唯一通路。

### 2.4 L4 跨会话检索

外部 MCP 服务 `memory-index/mcp-server.mjs`：把 **DSH 全部会话**（含工具调用记录）+ 项目文档 + 夜间摘要向量化（bge-small-zh-v1.5，512 维，SQLite + vectors.npy），检索 = 余弦相似度 + 关键词加分（每命中 +0.02，上限 +0.12）+ 同会话最多返回 2 条。模型侧工具名 `memory_search`。

预设 `dsh/agent-presets/qq-chat-v2/agent.cordis.yml` 末尾，原文：

### 2.6 唤醒提示词的拼装顺序（`src/bridge.js:12452`，原文一行）

```js
const base = roleLine + personaLine + fewshotLine + tokenLine + antiAiLine + proactiveLine
  + stickerLine + stickerNudgeLine + replyLine + statusLine + historyLine
  + (selfStatusLine ? `${selfStatusLine}\n\n` : '') + wakeLine + memoryLine + profileLine
  + participationLine + preSleepLine;
```

各段预算（实测/配置）：`personaLine` 每轮人格 1–2KB；`fewshotLine` 少样本 1–3KB；`historyLine` 预取历史 ≤1600 字符；`memoryLine` ≤1200 字符；`profileLine` ≤900 字符；`participationLine` 参与度摘要。**系统提示词的固定部分约 5–8K 字符**（≈4–6K tokens）。

## 3. 成本模型

### 3.1 计价（元 / 百万 token，非高峰；高峰时段（工作日 9:00–12:00、14:00–18:00）单价 ×2）

| 项 | deepseek-flash |
|---|---|
| 输入（缓存命中） | ¥0.02 |
| 输入（缓存未命中） | ¥1.00 |
| 输出 | ¥4.00 |

### 3.2 单步成本公式（这是全篇最重要的等式）

```
cost(step) = (cacheHit × 0.02 + cacheMiss × 1.00 + output × 4.00) / 1e6
input(step) = cacheHit + cacheMiss          // = 系统提示词 + 全部历史 + 新输入
```

含义：按本文对 DSH 请求路径的描述，每一步都会再次提交当时的上下文；因此输入 token 是主要成本乘数之一。简化估算为：
```
cost(一轮) ≈ 各 step 的（cacheHit × 命中单价 + cacheMiss × 未命中单价 + output × 输出单价）之和
```
这不是严格的“上下文体积 × 命中单价”：命中与未命中 token 的比例、输出 token、高峰价格和首轮缓存重建都会改变成本。步数减少通常能降低成本，但不能在未测量缓存与输出变化时直接按步数比例承诺收益。

### 3.3 实测：上下文已经很大

| 指标 | 值 |
|---|---|
| 当前主会话单步平均输入 | **264,274 tokens**（今日 155 次调用均值） |
| 上一代主会话（已退役）单步平均输入 | **402,908 tokens**（1227 次调用，累计 ¥17.39） |
| 当前会话历史长度 | 85 轮 / 2555 条记录 / 2.6M 字符 |
| 增长速率 | 第 1 轮 18K → 第 85 轮 314K，**≈3.5K tokens/轮** |
| 模型窗口 | 1,048,576 tokens |

推算（按 3.5K/轮、日均 ~42 轮）：从 314K 到 80% 窗口（840K）约需 **150 轮 ≈ 3–4 天**。届时 DSH 的内建压缩会介入，但其策略与阈值未知（见 4.4），因此无法预测届时成本与记忆保真度。

### 3.4 实测：静默轮是最贵的浪费

| 轮次区间 | 每轮步数 | 单步输入 | 输出 |
|---|---|---|---|
| turn 81–85（模型判定 `[SILENT]`，不说话） | **1** | **314,112 tokens** | **3–4 tokens** |

五轮静默合计消耗约 1.57M 输入 token，换回不到 20 个字符的输出（约 ¥0.031）。原因是：**"被叫醒 → 看一眼 → 判定不该说话"这个动作本身就要重放全部 314K 上下文。**

### 3.5 实测：步数是成本乘数

今日 289 次工具调用 / 85 轮（每轮步数中位 3，最长 25）：

| 工具 | 次数 | 说明 |
|---|---|---|
| `qq_wait_for_messages` | 99 | 每条结果仅 **449–842 字符**（p50 636），99 条累计 50,695；成本不在返回内容，而在「每调一次就多一步全量请求」 |
| `qq_send_message` | 96 | 必要 |
| `qq_mark_read` | 31 | |
| `qq_send_sticker` | 10 | |
| `qq_get_recent_messages` | 8 | |
| `qq_diary_write` | 8 | |
| `qq_get_unread_messages` | 6 | |
| **`qq_memory_append`** | **0** | 短记忆层从未被写入 |
| `qq_memory_query` / `qq_slang_query` | 1 / 1 | |
| `memory_search` | 4 | 跨会话检索，使用克制 |

极端案例：turn 77 一轮跑满 **18 步**，每步约 301K 输入 → 单轮约 **5.4M tokens**。

工具结果的**逐条**体积分布（v3 新增实测，完整表见附录 E）：289 条结果 p50 449 / p90 787 / 最长 14,791 字符；`>4,000` 只有 2 条（`memory_search` 4,018、`qq_get_prompt` 14,791），`>20,000` 为 0。也就是说 `tool-result-pruner` 的 50,000 阈值从未被触碰**不是配置失误，而是这份负载本来就没有长结果** —— 全部体积来自 289 条结果累积的 138,373 字符，被每一步原地重放。

## 4. 观测方法与证据等级

### 4.1 实测（可复现，代码与数据均在本机）

- 数据源 1：`state/token-usage.jsonl` —— 每步一行，样本：

  ```json
  {"k":"turn","t":1792936391072,"sid":"session-f3ade17a-...","key":"private:<uid>",
   "seq":2551,"turn":85,"step":1,"retry":0,"model":"deepseek-flash",
   "b":{"cacheMiss":179,"cacheHit":314112,"cacheWrite":0,"output":4,"reasoning":0}}
  ```

- 数据源 2：DSH 会话快照 —— 全量事件流（`user/message`、`assistant/message`、`tool/call`、`tool/result`、`agent/inbox/spliced`、`request/context`、`request/header`）。解压后 2555 条记录、85 轮。

  > 解压坑（供复现者参考）：该文件是 **1504 个连续 zstd 帧拼接**。Node 的 `zstdDecompressSync` 只解第一帧（得到 258 字节头），流式 `createZstdDecompress` 抛 `ZSTD_error_prefix_unknown`。正确做法是扫 magic `28 b5 2f fd` 得到各帧偏移，逐帧解压后拼接。

### 4.2 已知的统计口径陷阱（**重要**）

`state/token-usage.jsonl` 里除了 `k:"turn"` 的逐步明细，还有一批 `k:"base"` 的**累计值**行（103 条，其中一条 `cacheHit: 490,144,768`）。任何聚合都**必须** `filter(r => r.k === 'turn')`，否则数字虚高约 100 倍（实测：不过滤算出 ¥11.35，过滤后 ¥1.01）。另外存在 4 组重复行，需按 `sid|turn|step|retry` 去重。

### 4.3 推算（明确标注，不是实测）

| 结论 | 依据 |
|---|---|
| 成本与上下文体积成正比 | 计价表 + 单步输入实测 |
| 上下文约 3.5K tokens/轮增长 | 首末轮单步输入差 ÷ 轮数 |
| 轮换后单步 ≤40K | 各注入段预算之和（见 6.1 预期） |
| 日花费可降至 ¥0.3 以下 | 单步降幅 × 今日步数 |

## 5. 诊断（请逐条判断是否成立）

### Q1 · 上下文无上界，单步成本线性增长

- **现象**：单步输入 264K（当前）→ 403K（上一代会话）。会话一旦建立就永不轮换。
- **证据**：`ensureSession` 仅在 /reset、模式变更、DSH 侧丢失时退役（1.3）；2555 条记录里**没有任何 compaction 事件**。
- **代价**：¥20.51 中的 ¥17.39 花在"一个已经超大的会话"上。
- **根因**：系统把"记忆连续性"完全外包给了 L0 全量历史，而 L0 没有容量管理。

### Q2 · 静默轮为 4 个字符的决策支付 314K 输入

- **现象**：turn 81–85 每轮 1 步、输入 314,112、输出 3–4 token。
- **代价**：5 轮 ≈ ¥0.031；按日均比例外推，约占总花费的 3–5%（静默轮量大时更高）。
- **根因**：所有唤醒都走同一套"重放全部历史"的路径，没有"廉价前置判断"（第 9 节第 6 条讨论是否可加）。

### Q3 · 步数被等待类工具放大

- **现象**：`wait` 99 次（占工具调用 34%）；单轮步数最长 25（turn 77 一轮 5.4M tokens）。
- **代价**：每多一步 = 多一份完整上下文请求。步数是纯乘法。
- **根因**：① 提示词强制"沉睡前必须做一次完整观察"，静默轮也要走（代码级拦截见 6.3.0）；② `wait` 没有单轮次数上限；③ 每次 `wait` 返回的都是整份快照而不是增量 —— 但实测每条只有 449–842 字符，**问题不在返回内容大，而在于这一步本身就要重放 314K 上下文**。

### Q4 · 剪枝器从未生效过一次

- **现象**：`thresholdChars: 50000`；实测 289 条结果的分布是 p50 449 / p90 787 / 最大 14,791（`qq_get_prompt` 14,791、`memory_search` 4,018），**>4,000 仅 2 条，>20,000 为 0**。
- **结论**：`tool-result-pruner` 自上线起**零次生效**；`compaction-basic` 因 1M 窗口同样未触发（日志无事件）。
- **根因**：阈值是按"长上下文模型"直觉配的，没有对照真实工具输出分布标定。但更关键的是：**这份负载里根本没有长单条结果可裁**，唯一的大头是 289 条结果的累积 138,373 字符被每一步重放 —— 那是 O1 的问题，pruner 按单条阈值工作，结构上管不到。

### Q5 · L1 短记忆层空转，但成本照付

- **现象**：`qq_memory_append` 85 轮 0 次；`activeTopics`、`memberImpressions` 实测为空。
- **代价**：① 4 个工具定义常驻提示词（schema 约 600–800 tokens/步）；② 衰减逻辑（`memory-decay.mjs`）每轮空跑；③ 提示词里仍在教模型"记得写短记忆"，而它从不写 —— 这部分指令是纯 token 噪音。
- **根因**：把"记忆写入"设计成模型的自律行为，而模型在被唤醒的有限步数里优先做别的事。

### Q6 · 现有守门管不到这个失效模式

- **现象**：`dailyInputMax: 150M`，今日 41M；三条口径里没有"单会话上下文水位"。
- **结论**：成本在 3–4 天内会翻倍（第 3.3 节推算），而守门要到 3.7 倍才报警，且不拦截。

## 6. 方案

排序原则：**省下的钱 ÷ (改动风险 × 工作量)**。每一项给出：动机、具体改动、参数依据、预期、风险与缓解、回滚、验收、工作量。

### O1 · 上下文守门 + 会话交接轮换（核心，收益最大）

**动机**：Q1 / Q2。把"历史长度"从无上界改成有上界，且切换时保留必要的连续性。

**改动**：

1. 新增纯函数模块 `src/context-budget.mjs`：

```js
// 输入 = 本会话最近若干步的 { cacheHit, cacheMiss }（数据已在 token-usage，零额外请求）
// 输出 = 水位与动作建议
export function evaluateContextBudget(steps, cfg) {
  // 调用方必须先按 sid 过滤、去重，并按真实事件时间/序号排序。
  // 不能取历史最大值：那会让会话在曾经越线后永久保持高水位。
  const latest = steps.at(-1);
  if (!latest) return { watermark: null, level: 'unknown', ...cfg };
  const watermark = latest.cacheHit + latest.cacheMiss;
  const level = watermark >= cfg.hardAt ? 'hard'
              : watermark >= cfg.softAt ? 'soft' : 'ok';
  return { watermark, level, softAt: cfg.softAt, hardAt: cfg.hardAt };
}
// 初始候选值 softAt = 60_000, hardAt = 120_000；上线前用观测分布校准
```

2. 唤醒入口（`buildWakePromptV2` 之前）读水位：
   - `ok` → 正常运行。
   - `soft` → 记录 `[budget] 上下文 62K（soft）` 一类日志；可以追加“优先合并工具调用、避免非必要等待”的轻量提示。该提示不能替代工具侧硬限制。
   - `hard` → 置 `pendingHandoff = true`，**不在正在处理消息时立即换会话**，等待安全交接点。
   - `unknown` → 仅记录诊断日志，不自动轮换；避免日志缺失触发错误动作。

3. **交接轮换**（候选条件：距最后一条相关消息 ≥5 分钟，且距上次成功交接 ≥6 小时；上线前需确认群聊/私聊的活动时间来源和时钟语义）：

```
① 在当前会话中生成一次“不发送”的结构化交接内容：
   {"topics":[...], "openLoops":[...], "peopleChange":[...], "mood":"...", "insideJokes":[...]}
   约束：≤400 字；仅记录后续对话确实需要的内容；字段可为空；不得猜测缺失事实。
② 校验 JSON、长度、敏感信息与 schema 版本；无效结果不得覆盖最近一次有效交接。
③ 先写临时文件再原子替换 `state/handoff/{key}.json`；保留最近 3 份，并记录生成时间、来源 session、schema 版本和成功/失败状态。
④ 只有交接持久化成功后才 `retireSession(key)`；交接失败则保留旧会话并重试/告警，禁止先退役再写文件。
⑤ 下一次唤醒新建 session，并在 `memoryLine` 之后注入 `handoffLine`（初始预算 600 tokens，实际 token 数须观测）。
```

**参数依据**：
- 60K / 120K 是**初始候选阈值**，不是已证明的最优值。原文各段预算混用字符与 token，不能直接相加得出精确 token 数；上线前应以 `token-usage.jsonl` 的真实单步输入分布校准。
- 采用绝对阈值便于初期解释和告警；若未来切换上下文窗口不同的模型，再增加 `softRatio` / `hardRatio` 配置，但必须同时设置绝对上限，避免窗口扩大导致成本失控。
- 交接 ≤400 字是输出约束而非质量保证；必须通过人工连贯性抽查和失败场景测试验证。

**目标假设（尚未验证）**：希望把新会话稳态单步输入压到 40K 左右，并显著降低静默轮输入。原文的 `≤40K`、日花费 `¥0.15–0.25`、静默轮 `~25K` 都是推算，不是保证；实际结果取决于系统提示词、交接内容、工具结果、缓存命中和首轮缓存重建。上线报告必须同时给出均值、中位数、P95、静默轮单独分布及未命中 token。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 交接丢细节，手感断裂 | 交接 JSON 只放"必须知道的"；原文层由 `wake-history`（12 条）+ L2 档案兜底；轮换后 24h 人工抽查 3 个切换点的连贯性 |
| 交接 turn 本身要一次全量请求 | 只在水位超 hard + 安静期 + 6h 冷却时触发，按当前增速约每 2–3 天一次 |
| 前缀缓存重建，首轮全额未命中 | 已计入预期（新会话首轮约 18K 未命中 ≈ ¥0.018，远小于每次换来的节省） |
| 轮换期间丢消息 | 交接在安静期执行，期间新消息进队列，新会话继承 unread |

**回滚**：`contextBudget.enabled: false` 一键关闭（水位只记日志、不交接）。

**验收**：
- 单测覆盖空数据、重复行、重试、跨 session 混入、乱序记录、最新记录低于历史峰值等场景。
- 影子运行至少 24 小时：只计算并记录拟交接内容，不退役 session；人工检查交接准确性与敏感信息。
- 小流量启用后，新会话首轮水位目标为 `<60K`，但以实际分布报告，不把单个样本视为成功。
- 7 天观察日花费与水位的均值/中位数/P95；`<¥0.35/日` 作为待验证目标，不作为单一上线判据。
- 人工抽查至少 20 个交接点；任何丢失未回应消息、错误人物关联或隐私信息外泄均触发回滚。
- 回滚必须能恢复旧 session 映射或继续使用有效交接文件；不能只关闭开关却遗留半完成的退役状态。

**工作量**：1–2 天（含 `scripts/test-context-budget.mjs` 离线单测）。

### O2 · 让剪枝器真正生效 —— 实测后**建议撤销**（保留为已验证的反例）

**结论先行**：调 `tool-result-pruner` 的阈值**不会省到钱**。实测 289 条工具结果里只有 2 条超过 4,000 字符（`memory_search` 4,018、`qq_get_prompt` 14,791），把 `thresholdChars` 从 50,000 降到 4,000 至多裁掉这 2 条，合计不到 19K 字符 ≈ 6K tokens —— 相对单步 314K 输入是 2% 量级的噪声，而且这 2 条本身还有信息价值（`qq_get_prompt` 是提示词全文，裁掉等于自伤）。

**为什么 v1/v2 都判错了方向**：v1 看到 `wait` 累计 50,695 字符，推断「wait 返回太长、裁到 4,000 能省」；v2 认真质疑了 pruner 语义，但没有质疑**收益前提本身**。实测逐条分布后前提不成立：`wait` 单条只有 449–842 字符，`mark_read` 787，`send_message` 125，整份负载最长的一条是 `qq_get_prompt` 的 14,791。

**真正的体积在哪**：138,373 字符 / 289 条结果的**累积**，随 L0 全量重放，每步一次。这是 O1 的问题，不是 pruner 的问题 —— pruner 按单条阈值裁剪，结构上无法处理「条数 × 轮数」。

**如果仍想做工具结果生命周期管理**（可选，优先级最低）：需要的是「按轮数/按总量的老结果裁剪」机制。DSH 的 `tool-result-pruner` 不提供该能力（参数名即可判断是单条阈值语义）；自建等于在桥接层改写会话历史，收益与 O1 完全重叠而风险更大（破坏 DSH 侧一致性、影响缓存前缀）。**建议不做**。

**保留的验证动作（1 小时，作为否定证据留档）**：拿固定样例（短结果 / 长结果 / 结构化列表 / 尾部关键字段）跑一次插件，确认 `thresholdChars` 是单条语义、`headChars + tailChars` 如何解释，把结论写进 10.2 未知项表。确认后关闭该项，不必排进落地批次（见 §7 批次 1）。

**（原 v2 的候选参数与验证步骤保留在此，仅作为历史记录；按本节结论不排产）**

```yaml
tool-result-pruner:      # 原候选参数，已判定无效，勿上线
  config:
    thresholdChars: 4000
    headChars: 3000
    tailChars: 600
```

### O3 · 等待步瘦身

#### O3.0 现状代码事实（v3 新增实测，决定 O3 只能在什么范围内改）

1. **静默轮已经只有 1 步**：turn 81–85 每轮 `step=1`、输入 314,112、输出 3–4 token，模型直接输出 `[SILENT]`，由 reserved2 的「无行动兜底」（`src/bridge.js:13677` 附近）收尾。**静默轮没有可省的步数**，可省的只有它那一步的全量上下文 —— 那是 O1 的活，不是 O3 的。
2. **步数成本集中在活跃轮**：85 轮里步数中位 3、最长 25（turn 77 = 18 步 × ~301K ≈ 5.4M tokens）。每省掉一次 `wait` = 省掉一次整份上下文请求，这才是 O3 的收益单位。
3. **`mark_read` 有代码级拦截**：`POST /api/socialV2/mark-read`（`src/bridge.js:5313-5350`）在 `isSleepingConfigV2(wc) && preSleepWaitBlockedV2(st)` 时直接返回 400，错误原文是
   `还不能通过 qq_mark_read 直接回到潜水：还需等待约 N 分钟无新消息，或调用 qq_wait_for_messages(timeoutMs=300000) 完成一次沉睡前观察。`
   `preSleepWaitBlockedV2`（`src/bridge.js:9601-9615`）的放行条件只有四种：唤醒配置是 active / `anyMessage`、`preSleepWaitEnabled === false`、`hasExplicitEndV2(st)`、已安静满 `preSleepWaitMs`（默认 300000，本机 `socialV2.wake.preSleepWaitMs = 300000`）；此外 `preSleepWaitSatisfiedAt`（等待期间没人说话）或 `preSleepWaitObservedAt`（等待期间有人说话）已写入且其后无新消息也放行，这两个时间戳由 `wait` 工具的返回写入（`src/bridge.js:7295` / `7306`）。
   → 所以「静默轮跳过观察直接收尾」**不是提示词能解决的**，必须改 `preSleepWaitBlockedV2` 的判定口径；这也解释了 `preSleepLine` 那段提示词为什么存在（它是绕不过这层拦截的安慰剂）。
4. **`mark_read` 的游标本身上界**：`requestedReadThroughSeqV2`（`src/bridge.js:12204-12214`）要求 `throughSeq ≤ readThroughSeqV2(st)`（已展示连续消息水位），超过即 400；但**不传 `throughSeq` 时会走兼容路径清空全部 unread**（`acknowledgeMessagesV2`，`src/bridge.js:12218-12221`）。因此 v2 的顾虑应收窄成两条具体风险：(a) `throughSeq` 只保证「不超过已展示」，**已展示但未处理**的消息仍会被标已读 —— 这正是 `src/bridge.js:11205` 提示词要求「只确认你已处理的 readThroughSeq」的原因；(b) 省略 `throughSeq` 会一次否掉整队未读。

**改动**（分阶段）：
1. 先将 `wait` 返回改为增量摘要：`本次新增 N 条`，并附首尾各 2 条及明确的游标/时间范围；保证模型可按需调用 `qq_get_recent_messages` 补看。
2. 记录每轮 wait 次数与返回消息数；在测试环境验证调用上限候选值 2。
3. 只有确认消息游标、未读状态与处理顺序不变量后，才启用单轮 `wait` 上限；超过上限应安全结束当前 agent 步骤并保留未处理消息，不得仅返回错误后丢失控制流。
4. **静默轮不强制观察**（新口径，替换 v2 的「暂不采用」）：
   a. 先只改判定：`preSleepWaitBlockedV2` 增加「本轮判定为静默、且本轮未发送任何消息」的放行分支，同时保留 `preSleepWaitEnabled` 全局开关做一键回滚；
   b. `mark_read` 侧要求显式 `throughSeq`，拒绝省略路径（避免上一条 (b) 类整队误清空）；
   c. `throughSeq` 允许小于已展示水位（模型只确认它真正处理过的部分），日志记录 `markedCount` 与 `unreadCount` 的差；
   d. 观察「聊两句又潜水」是否回潮 —— `preSleepWaitBlockedV2` 的设计目的正是抑制这个，用灰度日志 + 人工抽查判定，不达标就回滚 a。

**目标假设**：每轮步数中位数可能从 3 降低；`−20~30%` 调用量与静默轮 `~25K` 都是待验证推算，需与 O1 分开测量，避免把组合收益归因给单一改动。

**验收**：至少 7 天观察 wait 次数、步数中位数/P95、未读队列积压、漏回/漏处理消息；人工抽查 20 轮。任何消息被错误标记已读即回滚相关改动。

### O4 · 短记忆要么自动化，要么删掉

**动机**：Q5。85 轮 0 次写入 = 该层当前是纯成本。

**方案 A（有条件推荐）**：`activeTopics` 由交接 turn 顺带产出（交接 JSON 的 `topics` 经 schema、去重和过期规则校验后写入 `social-v2.json`）。只有在确认没有外部调用者、旧提示词引用、控制台入口或用户工作流依赖后，才删除 `qq_memory_append/query/remove/list` 四个工具；删除前先提供兼容期/弃用日志。`memberImpressions` 并入 L2 档案也需要字段映射、去重和回滚迁移，不可直接丢弃原数据。

**方案 B**：桥接侧规则抽取 —— 投喂摘要时，从最近 30 条里取"被重复提及的名词 / 被 @ 的人"upsert `activeTopics`。模型不再写。

**取舍**：A 更省（少 4 个工具 schema + 一段提示词），但把"记忆写入"完全绑定在轮换上（若关闭 O1，L1 就没有写入者 → 接受，因为 L1 本来空转）。B 不依赖 O1，但规则抽取质量差。

**验收**：轮换后 `activeTopics` 非空且与最近话题相关；提示词 token 数下降。

### O5 · 档案抽取 backlog

**动机**：Q6 之外的记忆质量问题 —— `sliceMaxMessages: 40` 意味着抽取只看最近 40 条。聊得快时，中段内容会在被抽取之前滑出窗口，**永久丢失**。而 `extractCooldownMs: 30min` 在积压时反而拖慢。

**改动**：
1. 保留 `sliceMaxMessages: 40` 作为单次抽取上限；新增持久化游标/队列，按“尚未处理的消息区间”分片推进，而不是每次只看最近 40 条。
2. 每个分片成功抽取并完成档案写入后才提交游标；失败时可重试，且以消息 ID/区间保证幂等，避免重复条目或跳过消息。
3. 先明确 backlog 的保留上限和溢出策略。默认不静默丢弃最旧未处理消息；如必须限流，应记录被丢弃区间、条数和原因，并发出告警。
4. 冷却自适应可作为第二阶段：先记录 backlog 深度与抽取耗时，再验证 `pending < 30` → 30 分钟、`pending ≥ 30` → 10 分钟是否合适。
5. 质量门槛不变（`looksLikeBareLabel` / `scrubSensitive` / 6–160 字 / 必须带 evidence）；继续保持独立学习会话。

**风险**：分片推进增加游标持久化与重试逻辑复杂度，但避免单次 200 条输入的约 5 倍成本尖峰，也降低 backlog 永久丢失风险。`extractPerHour: 20` 保持为硬闸，是否需要调整须基于真实队列与成本数据。

**验收**：用模拟失败、重启、重复执行和 backlog 超限场景验证游标正确性；统计待处理数、最老消息年龄、成功/失败次数；抽查新档案条目均有 evidence 且非空泛标签。条目增长率只作为辅助指标，不可替代质量抽查。

### O6 · 摘要投喂可观测（2 小时）

**动机**：L3 是"潜水也知道发生了什么"的唯一通路，但今日日志里**一条相关记录都没有** —— 无法区分"今天没有群聊所以没触发"与"机制坏了"。

**改动**：加 3 个计数 + 3 条日志：入队（`[summary] 入队 n 条（待投喂 m 条）`）、投喂（`已投喂 k 条`）、作废（`silent 名额超时作废`）。

**验收**：群聊恢复后 24h 内能量出这三个数。

|---|---|---|---|
| 0 | O7 基础水位观测 + 指标口径核对 | 半天（原估算） | 先让当前水位、日累计输入、session 维度可区分；确认过滤 `k === 'turn'`、去重与排序正确 |

**总验收（小流量启用后至少 7 天）**：

- 报告单步输入均值、中位数、P95；目标 `<60,000 tokens` 是推算目标，不以均值单项作为通过条件。
- 报告日花费与高峰/非高峰分布；`<¥0.35/日` 是待验证目标，不得将其表述为已实现收益。

- 档案游标无静默跳跃，抽样条目均有 evidence；同时报告 backlog 深度与最老未处理消息年龄。
- 至少 20 个交接点人工抽查；无人物混淆、重要 open loop 丢失、消息漏处理或隐私泄露。
- 记录回滚演练结果、失败率、缓存未命中成本及首轮冷启动开销。
- 若成本改善但消息完整性或记忆质量变差，不视为验收通过。

## 8. 明确不考虑的方案（及理由）

1. **用向量检索替代 L2 档案**。现有档案是"具体事例 + evidence + 30 天半衰期 + 按类取 1 条"，比 top-k 片段召回的质量更高、且无额外延迟。跨会话语义回忆已由 L4 覆盖。若引入检索，会同时丢掉"时间衰减"与"证据约束"。
2. **每天定时 `/reset`**。会丢掉正在进行的玩笑、表情包语境、未回应的消息 —— 手感崩坏，且用户可感知。必须用"安静期 + 交接"。
3. **缩短 `contextWindow`（现有 20 条原文）**。20 条是对话连续性的下限；该省的地方是"不该说的话"（O1/O3），不是"听懂对方"。

## 9. 待决问题：修订后的明确建议

1. **顺序**：先做 O7 观测口径，然后直接进 O1 影子运行。**O2 已在 v3 实测否决**（6.2、附录 E），不要再为它排产；v2 里「先做 O2 验证、观察 3 天再决定 O1 是否紧急」的顺序建议作废 —— 历史全量重放和水位增长已有直接实测证据，O1 不依赖 O2 的结论。
2. **阈值**：60K / 120K 可作为初始候选值，不是已证实最优值。第一版建议绝对阈值 + 可配置窗口比例的设计预留；上线初期以真实分布和预算目标校准，未知或缺失数据不触发自动退役。
3. **交接内容**：保留 `topics`、`openLoops`、`peopleChange`、`mood`，增加可选 `insideJokes`（最多 3 条），但只保留有上下文依据、不会暴露敏感信息的内部梗。输出必须允许字段为空，不得为填满字段而编造。
4. **O4 取舍**：倾向方案 A，但删除工具前先检索全仓调用点、提示词引用、控制台入口和文档依赖；采用“先停用/弃用并记录调用，再删除”的迁移步骤。`memberImpressions` 并入 L2 前必须完成迁移映射与备份。
5. **O1 替代**：目前不能确认 `compaction-basic` 的触发阈值、保真策略或能否按 60K 控制，因此不能据此替代桥接层交接。建议并行做最小验证：用固定会话和样例观察压缩事件、前后上下文、历史可回忆性与成本；在得到证据前，桥接层守门仍作为可控方案，但先影子运行。
6. **静默轮能否不调模型**：先实现低风险规则降频和可观测，不立即引入小模型。规则候选包括连续静默后逐步延长 proactive 唤醒间隔；任何过滤都必须保留被 @、明确提问和未处理消息等高优先级触发。
7. **O5 backlog 上限**：采用每次最多 40 条、持久游标推进的分片抽取，不建议单次输入 200 条。若 backlog 超限，不得静默丢弃最旧消息；必须显式告警并记录溢出策略。
8. **预算感知提示词**：值得做，但采用确定性优先级裁剪，不要随机删段。先定义段落优先级（系统/安全约束与当前消息最高；必要历史、交接和档案其次；表情包推荐、非必要 few-shot 等低优先级），再按预算从低优先级段开始裁剪，并记录每轮被裁剪的段落。应以同一组测试对话验证行为差异。
