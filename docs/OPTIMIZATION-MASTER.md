**两份方案的共同结论（本文最重要的判断）**：

1. **两边的头号问题都不是「策略不够多」，而是「没有度量」。** 表达层只有一行行日志，答不出哪条规则最常触发；成本层守门只看日累计 150M，给不出上下文增长期的任何早期信号。
2. **两边的头号病根都是「无上界累积」**：规则只增不减；会话历史只增不减（压缩能力存在，但从未被触发）。

3. **所以顺序只能是：先统一观测口径 → 再做结构性改动 → 最后做质量打磨。** 反过来（先堆规则 / 先调阈值）会得到无法归因的改动。

**三条已被数据推翻的做法，不要重犯**：

- 调 `tool-result-pruner` 阈值省钱：这类负载里单条工具结果的中位数只有数百字符，超过 4,000 字符的是个位数条、超过 20,000 字符的一条也没有 —— `thresholdChars: 50000` 从未触发**不是配置错误，而是负载里没有长结果**；真正的体积是数百条结果的**累积**（十几万字符）被每一步重放 → 只能由 O1 轮换解决。
- 「静默轮跳过沉睡前观察」靠改提示词解决：代码层被 `preSleepWaitBlockedV2` 拦住，提示词绕不过去。
- 靠 15 条固定样本证明采样参数更自然：那 15 条直接喂给过滤器，与温度无关。

## 1. 系统底座与共同口径

### 1.1 拓扑

```
QQ 客户端 ──(OneBot 协议)──▶ qq-bridge（Node 常驻进程）
                                   │  一个「会话 key」↔ 一个 DSH session
                                   ▼
                             DSH（agent 运行时 + 模型网关）
                                   │
                                   ▼
                        deepseek-flash（1,048,576 token 窗口）
```

- **一个 QQ 会话（私聊或群）= 一个 DSH 会话**，映射以键值对持久化（键 = 平台会话标识，值 = 会话 id）：
  `{"sessions":{"private:<QQ号>":"session-<uuid>"}}`。
- 机器人有固定人格（角色卡驱动），不聊天时「潜水」，由定时唤醒 + 触发条件（被 @、关键词、提问、随机概率）叫醒。
- AI 的文本输出**不会**自动发到 QQ，必须调用工具（`qq_send_message` 等）显式发送。这是「醒来看一眼再决定不说话」的前提。

### 1.2 一轮的生命周期（成本结构的根源）

```
消息到达
  → 触发唤醒（reason: message / proactive / timeout / replyCheck …）
  → buildWakePromptV2() 组装一条提示词（17 段，顺序固定）
  → deliverPrompt() 送进 DSH 会话
  → 模型输出：① 调工具（发消息 / 等待 / 查档案…）→ 回到上一步，这是「第 2 步」
              ② 结束本轮，设置下次唤醒条件
```

> **关键事实（整个成本层方案的根源）**：DSH 不在服务端保存跨轮对话状态。**每一「步」都是一次完整的 LLM 请求**，输入 = 系统提示词 + 该会话截至目前的全部历史 + 本次新增。证据：逐步 token 记录里每一步的输入都约等于当时的历史总量，且随轮次单调增长（§3.3）。

一次唤醒若调用 3 次工具，就是 3 次请求，每次都重放同样体积的历史。工具结果、历史消息、注入段落全部按「条数 × 轮数」被重复计费。

### 1.3 会话生命周期：只有四种退役

```
ensureSession(key):
  既有 session 且代际匹配 → 直接复用（正常路径，永远复用同一个 session）
  仅在以下四种情况 retireSession()：
    ① 用户 /reset  ② 控制台「清上下文」  ③ 模式/权限变更  ④ DSH 侧会话丢失
```

**没有任何按轮数 / 时间 / 体积的自动轮换。** 这是 Q1 的直接成因。

### 1.4 定义与统计口径（读任何数字之前先看这节）

| 术语 | 定义 |
| --- | --- |
| **步（step）** | 一次 LLM 请求。一轮对话 = 1..k 步 |
| **轮（turn）** | 一次唤醒，从组装提示词到结束 |
| **上下文水位（watermark）** | 同一 session **最近一条有效** `k:"turn"` 记录的 `cacheHit + cacheMiss`。**不是历史最大值** |
| **静默轮** | 模型判定 `[SILENT]`、不发送任何消息的唤醒轮 |
| **无输出轮** | 本文新增的合并指标 = 静默轮 + 群聊被兜底丢弃的发送（见 §4-X5）。两套优化都在减少输出，必须合并观测 |
| **交接（handoff）** | 轮换会话前，让旧会话产出一段结构化摘要，供新会话首轮继承 |
| **silent turn** | 不发送、只用于「让模型记住」的注入轮 |

**两个必踩的统计陷阱（`[已验证]`）**：

1. token 用量文件里除逐步明细 `k:"turn"` 外，还有一批 `k:"base"` 的**累计值**行，其字段数值可达数亿。任何聚合**必须** `filter(r => r.k === 'turn')`，否则金额会虚高一个数量级以上（曾观察到约 10 倍的偏差）。
2. 同一步骤可能存在重复行，需按 `sid|turn|step|retry` 去重；水位必须先按时间/序号排序再取最新，乱序会把「曾经越线」当成「现在越线」。

字符 ≠ token：预算体系里混用字符与 token（人格卡按字符计、注入 ≤2,600 字、`memoryLine` ≤1,200 字 vs 交接 ≤400 字/600 tokens）。**不得把字符数直接当 token 数做精确推算**，只能当预算上界。

## 2. 表达层：去 AI 感

### 2.1 问题拆解：AI 感是可测量的四件事

**结论**：AI 感不是「用了几个坏词」，而是四个可测量的东西 —— **句子太长、结构太完整、句式在替对方总结情绪、节奏太像一个随时在线的东西**。

| 来源 | 典型表现 | 强制力 |
| --- | --- | --- |
| 结构 | 一条塞三句、总分总、结尾升华 | 部分（只有提示词劝，没有硬闸门） |
| 句式 | 把对方的话总结成情绪形容词再评论；宣布共情；客服收尾 | 只有最标准的几种被正则拦住 |
| 词汇 | 书面腔（因此/例如/是否）、互联网黑话（赋能/闭环）、程度副词刷量 | 是（确定性替换） |
| 格式 | Markdown 星号井号、列表、引用块、句号 | 是 |
| 节奏 | 秒回、每条都回、从不漏看、打字速度恒定 | 部分 |
| 模态 | 表情包当唯一回复、每条都挂「～哦啦呀」、TTS 播音腔 | 弱（无发送层约束） |

**关键判断**：正则能管住一部分「词」和「句式模板」，但难以可靠判断上下文、语义完整性和自然度。优化重点不应只是继续堆词表，而应优先建立**度量闭环 + 语义保真检查 + 风险分级过滤**。

### 2.2 四层夹击：强制力只来自第三层

```
群消息 → 桥接判定唤醒
       → 拼唤醒提示词（17 段固定顺序）
       → DSH agent（qq-chat-v2 预设）生成工具调用
       → 采样代理（注入 temperature/top_p/penalty，关 thinking）
       → qq_send_message / qq_reply / qq_send_burst
       → sendToQQ / sendMessagesV2 / v1 burst 循环
       → deslopOutgoing()   ← 硬过滤在这里，唯一强制点
       → 脱敏 → 长度闸门 → splitForQQ() → OneBot → QQ
```

| 层 | 作用 | 手段 |
| --- | --- | --- |
| 1 提示词（劝） | 告诉模型「照这个样子说」 | 人格卡 + 每轮注入 |
| 2 行为预设（改动作） | 管分条、漏看、拒绝有求必应、别当心理咨询师 | `qq-chat-v2` 预设 |
| 3 发送层（不许说） | 模型说了也发不出去 | `deslopChatText` 确定性删改 |
| 4 素材/采样（换底子） | 真人样例 + 高温度低重复 | few-shot + 采样代理 |

**必须承认的边界**：发送层规则虽可确定性执行，但不代表每条规则都正确；**错误的硬过滤同样会稳定地产生误伤**。优化目标是表达自然、语义完整、行为合宜，而不是单纯缩短或删除文本。

三个出口，三处都接了（实现层面的不对称，改发送逻辑时要留意）：

| 出口 | 覆盖范围 | 包装 |
| --- | --- | --- |
| `sendToQQ(key, msg)` | 一代模式、系统播报以外的所有通知 | 先洗后脱敏 |
| `sendMessagesV2(...)` | 二代 MCP 发送、burst、定时提醒 | 先洗后脱敏 |
| v1 burst 循环 | 一代连发 | **只洗、未包脱敏** |

`deslopOutgoing(key, raw)` 的统一行为：

- 读配置 `aiTone`，`enabled:false` 直接短路。
- 以 `⚠ ⏳ ⏹ 🔐 ❓ ✅ ❌ ⏰`、`agent`、`系统` 开头的**告警类文本不动**，避免把运维通知洗坏。
- 命中写一行日志：`去AI味 <key> [命中规则id] 原文前40字 → 清洗后前40字`（已脱敏）。
- 清洗后为空或判空时进入兜底决策（六档，见 §2.5.4）。

### 2.3 提示词层

#### 2.3.1 人格卡结构

| 小节 | 内容 | 进不进每轮 |

| 一、你是谁 | 身份、雷点、彩蛋、最高原则 | 否（走 `qq_get_prompt`） |
| 二、群聊说话铁律：去 AI 味 | 17 条：长度、不总结、允许跑题、允许只发「？」、被问 AI 怎么答、不有求必应、可装傻 | 否 |
| 三、说话方式：去 AI 味 | 10 条：短句像打字、少括号、少句号、少表情、不要客服腔 | 否 |
| 四、节奏与消息习惯 | 9 条：一句一条、隔几秒补、改口、对方没说完先等、结束前再等 5~10 分钟 | 否 |
| 五、人格与梗 | 傲娇、偷吃 token、服务器繁忙、偶尔摆烂 | 否 |
| 六、AI 味黑名单：出现即失败 | 六类：心理师腔 / 客服腔 / 八股拔高 / 黑话 / 标点 / 其他 | 否 |
| 七、回复示例 | 15 组「你不要 / 你可以」对照 | 否 |
| 八~十 | 群文化自适应、热闹时保持节奏、你的样子 | 否 |
| **核心 · 每轮必看** | 449 字符 | **是，每次唤醒** |
| **场景 × 8** | 情绪倾诉 / 被问是不是 AI / 冷场 / 求推荐 / 被怼 / 深夜 / 群聊接梗 / 正经问题 | **是，按路由命中，每轮最多 2 个** |

注入预算：全文上限 `maxInjectChars=8000`（卡片约 7 千字符，不截断）；每轮核心+场景上限 `wakeInjectMaxChars=2600`。

#### 2.3.2 核心段原文（每轮都注入，449 字）

```
## 核心 · 每轮必看
- 你是 DeepSeek，混在群里的群友，不是客服、不是助手、不是心理咨询师。
- 一条 1~10 字，一行一条；想补就再发一条，不写小作文。
- 接话顺序：接梗 > 反问细节 > 阴阳 > 认真答；"？""6""草""乐"都算回。
- 每轮不必回；没人理就自说自话，或者继续潜水。
- 被问是不是 AI：大方认，玩梗，不解释模型。
- 被怼：顶回去；被叫蓝色大肥鱼就炸毛。
- 不打包票、不给人生建议、不总结升华、不每条都挂"～哦啦呀"。
- 不用句号、不用 Markdown、不用括号内心戏。
- 黑名单：这话听着挺沉的 / 我理解你的感受 / 希望对你有帮助 / 首先其次最后 / 综上所述 / 作为一个AI
- 嘴贫但有分寸：对群友可以损，对管理员正常说话、语气温柔；玩笑点到为止，别真把人弄急。
示范：群友"最近好累啊"→"那上班记得带贡品"；"我分手了"→"该"；"在吗"→"不在"；"@你"→"别@你爹了"
```

#### 2.3.3 黑名单六类（压缩）

- **心理师腔**：把对方的话总结成情绪形容词再评论（「这话听着挺沉的」「听起来你最近……」）；宣布共情（「我理解你的感受」「你的感受是合理的」「允许自己」「慢慢来」「稳稳地接住」「情绪价值」「狠狠共情」「我在这里陪着你」）。
- **客服腔**：「希望这个回答对你有帮助」「有问题随时问我」「祝你今天顺利」「以下是几点建议」「作为AI」「作为一个语言模型」「这是个好问题」。
- **八股与拔高**：首先/其次/最后、综上所述、总而言之、值得注意的是、不得不说、说白了、换句话说、本质上、接下来我们看看。
- **互联网黑话**：赋能/助力→帮、打造/深耕→做、闭环→完整流程、底层逻辑→根本原因、抓手→办法、降本增效→省钱、颗粒度→粗细、护城河→优势、生态位→位置。
- **标点**：一句话不写句号；不用冒号/破折号/双引号堆解释；不用 Markdown。
- **其他**：「大家今天有什么安排吗」「你们觉得呢」「记得……哦」「加油！」、每句都挂「～哦呢啦呀」、自称「本小姐」、用「或者」给并列清单、「行吧 正经的」式自我修正、「行，」「好的，」开场接话。

#### 2.3.4 正反例（15 组里挑 5 组）

| 群友说 | 你不要（AI 腔） | 你可以（人味） |
| --- | --- | --- |
| 最近好累啊 | 这话听着挺沉的，最近是不是压力太大了？我理解你的感受，允许自己休息一下。 | 多大了 还累 / 累就对了 说明在长个子 |
| 我分手了 | 我能感觉到你很难过，慢慢来，你的感受都是合理的。 | ？ 谁提的 / 分就分 下一个更乖 |
| 来点推荐 | 推你一首《我是一条小鲸鱼》 保证解压 | ？ 你要啥推荐 / 退钱吗 / 刚吃完饭 别问我 |
| 你到底是人是AI？ | 我是DeepSeek，一个AI助手，很高兴为您服务。 | 我是DeepSeek 小鲸鱼，V我50解锁高级对话 / 你猜 |
| 行行行 你赢了 | 本来就是 我只是懒得跟你争（赢了还补刀） | 赢就赢呗 我又不掉肉 / 行吧 这局让你 下一局再说 |

写法的三个要点：**短**（1~10 字）、**接梗优先于共情**、**允许不满足对方**（反问/装傻/给离谱答案）。

#### 2.3.5 每轮实时拼装（顺序固定，17 段）

```
角色行 → 【人格 · 每轮】→ 【接话参考】few-shot → 【会话令牌】→ 【反AI味】
→ 【积极性】→ 表情包策略+推荐 → 【首回复节奏】→ 【此刻状态】→ 历史
→ 唤醒条件 → 记忆 → 交接摘要 → 群友档案 → 参与提示 → 【沉睡前强制等待】
→ 具体唤醒原因段
```

其中与 AI 感直接相关的两段：

```
【反AI味】你不是客服：不用有求必应，可以装傻、已读乱回、拒绝推荐；少用“一绝/真管用/保证/绝对”这类词。

【积极性】不要习惯性潜水：群里有你能接的话题就主动参与，偶尔插一句别人的话题也很正常；
只有确实没话可说、对方已明确结束、或长时间没人说话时才潜水。
```

表情包策略（同样是「像不像人」的一部分）：合适时机用、约每 1~2 轮一张（`nudgeEveryAiTurns=2`）、优先用备注能对上语境的、一条只能一张不能带字、严肃话题不硬塞、不总用同一张、不拿表情当唯一回复。

#### 2.3.6 场景路由与风格手册

- 路由只看确定性信号（场景路由模块）：最近 8 条消息的关键词（分手/难受→情绪倾诉；你是AI吧→被问是不是AI；推荐/安利→求推荐；骂人→被怼；报错/怎么解决→正经问题）、0~5 点→深夜、群安静 ≥20 分钟→冷场，兜底→群聊接梗（私聊兜底→情绪倾诉）。
- 命中后注入对应 `## 场景：xxx` 段，每轮最多 2 个，日志打印 `[人格] <key> 场景=[…]（原因）注入 N 字符`。
- 8 篇风格手册（每篇 ≤2000 字符）模型主动调 `qq_style_guide(topic)` 才读，不占每轮预算。结构统一：`摘要：` + 先分真假 + 怎么接 + 反例（出现即失败）+ 好例子。例：《情绪倾诉》要求「问具体的，别总结感受」——问「谁提的」「多久了」，不问「你还好吗」。

#### 2.3.7 真人 few-shot 素材

- 两层素材：**手写样例**（按标签分文件，一份一组）+ **导入样例**（从平台导出的聊天记录里自动切分）+ 一份索引；
- 每轮按当轮群聊内容挑 2~4 条最像的注入，预算 ≤900 字符；最近 12 条用过的回避，避免每轮看同一批。
- 手写格式：一个空行一组，`# 标签 标签`，`群友：…` 是别人，`我：…` 是机器人，**每组最后一行必须是「我：」**，回复 ≤30 字。
- 导入：一条脚本，指定「自己的昵称」，把导出文本切成「我：/对方：」成对样例；私有导出格式（加密库）读不了，会直接报错——这是设计上的挡板，不是缺陷。
- 开关 `style.fewshot.enabled`。

**为什么有效**：模型对**样例**的模仿强于对**禁令**的遵守。人格卡说「不要总结升华」，不如给一条「累了就睡 醒了继续累」。

#### 2.5.4 兜底六档（P0-2 落地形态）

| 档 | 条件 | 动作 | 日志 |
| --- | --- | --- | --- |
| `normal` | 无 fallback，`removed ≤ 0.6` | 发清洗后文本 | 现有日志 |
| `heavy` | 无 fallback，`removed > 0.6` | 仍发清洗后文本，记 flag 供复核 | `去AI味-heavy` |
| `keep-raw` | fallback 且 `substantive(raw)` 为真 | **发原文**（不发「嗯」） | `fallback-keep-raw` |
| `nudge` | fallback 且非实质，`mode=nudge` 或私聊 | 发 `fallbackText`（默认「嗯」） | `fallback-nudge` |

| `off` | `mode=off` | 返回空串交给上层 | — |

`substantive(raw)` 判据（任一即可）：含数字（`\d`）、含链接或 `@`、含反引号代码、含否定词（不/没/别/未/勿/甭）、或长度 ≥ 12 字。**宁可这次不洗，也不能把一条有信息的消息洗成「嗯」。**

配套：四个 HTTP 发送接口在丢空时回 `sent:0` + `skipped` + 可执行 `hint`（"被判成AI腔（删空），已丢弃未发送。别原样重发…"），避免模型把丢空当成发送故障反复重试。

```json
  "fallbackPolicy": { "mode": "skip", "keepRawIfSubstantive": true, "nudgeInPrivate": true, "fallbackText": "嗯" }
}
```

#### 2.5.5 设计取舍（五条硬约束）

1. **只删不改写**：后处理不做 paraphrase，否则等于第二次生成，一致性和延迟都崩。唯一例外是 `我理解你的感受 → 懂`（1:1 且语义等价）。
2. **确定性、可复现**：同一句话永远同样处理，方便测试与排错；不引入随机。
3. **可解释**：每条规则带 `id` 和 `why`，日志只报 id，`listRules()` / `listBannedWords()` 供控制台展示。
4. **语义保真优先**：删除或替换后必须检查是否留下残句、丢失否定/数字/专有名词，或改变原意；无法确定时优先保留原文并记录待审。
5. **规则按风险分级**：格式清理、明确模板清理和上下文相关语气词不得共用同一自动删除策略。有歧义的表达先统计和人工评估，再决定是否启用改写。

#### 2.5.6 长度闸门（P0-4 落地形态）

`planLengthSplit` 四态 `none / split / warn / skip`：

- `>40` 字且存在**安全边界**（段落、完整句、清晰意群）才拆；`>60` 字无边界只告警。
- 代码 / 反引号 / URL / 告警前缀 / 结构化多行一律 `skip`，不拆。
- 最多拆一次、`maxParts=2`、两段都 ≥`minPartChars=6`；拆条后间隔重算。
- 引用 / `@` 只挂第一条。
- 四条出站路径（`sendToQQ`、`planSocialTimeline`、`sendBurstToQQ`、`sendMessagesV2`）都过闸门。

#### 2.6.1 发送节奏（当前值）

P1-1 的延迟公式：`delay = clamp(300 + 45 × 字数, 600, 4000) × U(0.8, 1.2)`，`auto` 与 `burst` 间隔共用。

**旧问题（已按 P1-1 改掉）**：间隔曾是**与内容长度无关的固定随机**。真人打字时间 ≈ 字数 × 40~90ms，长句必然更慢，这是最容易被人眼识别的信号之一。

**新问题（未验证）**：公式是候选模型，不是已验证的真人模型。需验证延迟分布、上下限、队列拥塞与异常恢复；不要把「看起来像真人」当伪造身份的理由，也不要用随机延迟掩盖系统问题。

### 2.7 规则覆盖的已知边界（15 条样例）

用 15 条常见 AI 腔句子作为静态样例喂给 `deslopChatText`（默认配置），**5 条被改写、10 条原样放行** `[已验证]`：

| 输入 | 输出 | 命中 |
| --- | --- | --- |
| 听着就累，最近压力很大吧 | 原样 | — |
| 说真的，你已经做得很好了 | 原样 | — |
| 其实吧，这种事急不来 | 原样 | — |
| 你不用解释，我懂 | 原样 | — |
| 这事儿确实挺压人的 | 原样 | — |
| 换个角度想，这也是成长 | 原样 | — |
| 反正都过去了，往前看 | 原样 | — |
| 我也经历过，特别理解 | 原样 | — |
| 你先别急，慢慢说 | 原样 | — |
| 抱抱，会好起来的 | 原样 | — |
| 听起来你最近挺累的 | 你最近挺累的 | `sounds-like-you` |
| 希望对你有帮助 | **嗯** | `hope-helpful-2` + fallback |
| 首先，我们要明确目标。其次，分步执行。 | 我们要明确目标。分步执行。 | `connectors` |
| 好的，我看一下 | 我看一下 | `agree-opener` |
| 这个功能非常强大，非常规情况除外 | 这个功能强大，非常规情况除外 | `degree-adverb` |

两个直接结论：

1. **漏网的是「同义变体」**。骨架式正则管不住换词的说法：「听着就累」「这事儿确实挺压人的」全躲过去；「我也经历过，特别理解」是「我理解你」的变体，正则只认后者。
2. **`希望对你有帮助` 被整条删成「嗯」**。这比原句更怪：一个人不会无缘无故发「嗯」。这正是 P0-2 兜底三分/六档的由来。

**证据边界（必须保留）**：以上只说明这组输入下的规则行为，**不能代表线上命中率、误伤率或用户感知**。这 15 条是构造样例，不是抽样统计，重复运行结果一致。

**另一条重要提醒**：这 15 条不是「应该全部删掉」。像「你先别急，慢慢说」「抱抱，会好起来的」删了会更假——真人也会这么说。规则的作用是**降低频率**，不是清零。

**实现时配套的三组回归**（缺一不可；通过与否以实际运行为准，本方案不预置结论）：

- 规则层：既有规则的改写行为不被新逻辑破坏（正例/反例/边界）。
- 兜底与闸门层：六档决策、语义保真、幂等、统计写入。
- 长度闸门层：四态判定，以及「不该拆的不要拆」的边界。

**影响面审计**：

- **不受影响**：发图、发贴纸、发语音、拍一拍、头像/签名/资料、合并转发读取 —— 它们自己拼 OneBot segment 数组直连网关，不经过 `deslopOutgoing` / `planLengthSplit` / `sendMessagesV2`。
- **自动语音的判定在闸门之前**：用拆条前的 `messages.length === 1` 决定语音是否顶替文字，因此「单条短句转语音」不受长度闸门影响。
- **可见变化（预期内）**：①群聊整条 AI 客套被丢弃不发；②>40 字且有安全边界的长句拆成两条；③连发间隔按上一条字数。

- **回归范围**：媒体类能力（发图 / 贴纸 / 自动贴纸 / 自动语音 / 语音 / 音量）、桥接审计、风格手册与场景路由各有一组用例。改动前必须先立基线，否则无法区分「新引入的失败」与「既有失败」。

## 3. 记忆与成本层

### 3.1 记忆的五层 + 两条补历史腿

| 层 | 载体 | 目的 | 注入方式 | 现状与薄弱点 |
| --- | --- | --- | --- | --- |
| **L0 会话原文** | 会话磁盘快照 | 具体对话连贯性 | 全量重放（无裁剪） | 体积随轮次线性增长，是本层成本的主因 |
| **L1 短记忆** | 状态文件 | 正在聊的话题、想说没说的话、对人的即时印象 | 拼进唤醒提示词 `memoryLine` | **常为空**：写入完全依赖模型主动调用，模型很少主动写 |
| **L2 长档案** | 档案文件 | 长期人设/关系：具体事例 + 证据 + 时间衰减 | 拼进 `profileLine`（≤3 人 / ≤900 字） | 在用，但只覆盖被主动提到的人 |
| **L3 摘要投喂** | 内存队列 | AI 潜水期间群里发生了什么 | 一次性 silent turn 灌进同一会话 | 启用率低，观测口径缺失 |
| **L4 跨会话语义记忆** | 独立向量索引 | 回忆「以前某次会话」 | 模型主动调检索工具 | 使用克制 |
| 补腿 A 掉线补拉 | `catch-up` | 重连后补回错过的消息 | 最多 5 会话 × 50 条，10s 总预算 | 正常 |
| 补腿 B 唤醒前预取 | `wake-history` | 补上「醒来前」的最近对话 | 12 条 / ≤1600 字 / 2.5s 超时 | 正常 |
| 日记 | 日记文件 | 一天一页的自我叙事 | **不进提示词**，只影响行为摘要 | 按天累积 |

**L1 衰减参数**（`DEFAULT_DECAY_CFG`）：

```js
{ halfLifeDays: 7, pendingFloor: 0.35, foldThreshold: 0.15, foldMinCount: 3,
  maxChars: 1200, expiredGraceHours: 24 }
```

结构上限：`activeTopics` ≤20 条且 24h 未再提即删；`pendingThoughts` 默认 2h 过期；`memberImpressions` ≤50 人。**写入完全依赖模型主动调用 `qq_memory_append`** —— 这是它空转的根因。

**L2 长档案参数**（`PROFILE_DEFAULTS`）：

```js
{ settleIdleMs: 360000, sliceMaxMessages: 40, sliceMinMessages: 6,
  extractCooldownMs: 1800000, extractPerHour: 20,
  maxPeople: 200, maxRecordsPerPerson: 80, maxTermsPerGroup: 120,
  halfLifeDays: 30, pruneWeight: 0.12, pruneAfterDays: 120,
  injectMaxPersons: 3, injectMaxChars: 900 }
```

质量约束：只接受具体事例 —— 文本 6–160 字、必须带 ≤80 字 `evidence`、`looksLikeBareLabel()` 拦掉「他很友善」这类空泛标签、`scrubSensitive()` 脱敏。抽取由**独立「学习会话」**执行（工具集只含档案读写），不污染主对话。

**L3 摘要投喂**：AI 潜水/观望期间消息不丢弃，进 `pendingSummaries`（每会话 ≤60 条），随后用一次 silent turn 灌进**同一个 DSH 会话**：

```
【群聊摘要】过去一段时间群里发生了这些（你未逐条参与）：
<若干行 发送者：文本>
【最近对话】
<最近 20 条>
你不需要回复，只需记住这些内容，后续聊天会更自然。
```

silent 名额 5 分钟未消费即作废（`SILENT_TURN_TIMEOUT_MS = 300000`）。这是「潜水也知道群里发生了什么」的唯一通路。

**L4 跨会话检索**：把全部会话（含工具调用记录）+ 项目文档 + 夜间摘要向量化（bge-small-zh-v1.5，512 维，SQLite + vectors.npy）。检索 = 余弦相似度 + 关键词加分（每命中 +0.02，上限 +0.12）+ 同会话最多 2 条。

**上下文压缩能力存在但从未生效** `[已验证]`：预设在末尾挂了 `compaction` 组（`compaction-basic` + `command-compact` + `tool-result-pruner`，后者 `thresholdChars: 50000` / `headChars: 45000` / `tailChars: 2000`），但 `src/` 里**没有任何代码主动触发压缩**，也没有 `/compact` 控制台入口，会话记录里没有任何 compaction 事件。

### 3.2 成本模型

计价（元 / 百万 token，非高峰；高峰时段（工作日 9:00–12:00、14:00–18:00）单价 ×2）：

| 项 | deepseek-flash |
| --- | --- |
| 输入（缓存命中） | ¥0.02 |
| 输入（缓存未命中） | ¥1.00 |
| 输出 | ¥4.00 |

```
cost(step)   = (cacheHit × 0.02 + cacheMiss × 1.00 + output × 4.00) / 1e6
input(step)  = cacheHit + cacheMiss      // = 系统提示词 + 全部历史 + 新输入
cost(一轮)   ≈ Σ 各 step 的（命中输入 + 未命中输入 + 输出）
```

**这不是严格的「上下文体积 × 命中单价」**：命中/未命中比例、输出 token、高峰价格、首轮缓存重建都会改变结果。步数减少通常能降成本，但**不能在未测量缓存与输出变化时按步数比例承诺收益**。

### 3.3 成本结构的量级（量级示意，非承诺值）

只看一个代表性观测窗口的**形状**就能定位问题；下表全部是量级，不含任何具体部署数据：

| 指标 | 量级 | 含义 |
| --- | --- | --- |
| 单步平均输入 | 数十万 token | 一次工具调用 = 一份完整上下文；历史越长，每一步都越贵 |
| 会话历史 | 数百轮、数兆字符 | 全量重放、无裁剪 |
| 增长速率 | 每轮数千 token（约 3–4K） | 与会话轮数近似线性 |
| 模型窗口 | 1,048,576 token（模型公开规格） | 到 80% 窗口约百余轮；按日均数十轮计，只需数天 |
| 花费集中度 | 单个未轮换会话占累计花费 **80% 以上** | 钱主要被「一个永不轮换的会话」烧掉，不是被「话多」烧掉 |

**静默轮是最贵的浪费**：

| 场景 | 每轮步数 | 单步输入 | 输出 |
| --- | --- | --- | --- |
| 模型判 `[SILENT]` 的轮 | 1 | 与正常轮同量级（数十万 token） | 个位数 token |

「被叫醒 → 看一眼 → 判定不该说话」这个动作本身就要重放全部上下文：上下文越大，一次沉默越贵。连续几个静默轮，累计输入可达百万 token 量级，换回不到二十个字符。

**步数是成本乘数**：每轮步数中位数是个位数，极端轮次可达 20 步以上；每多一步 = 多一次完整上下文请求。工具调用结构上，**等待类工具次数最多（约三分之一）** —— 它的返回内容很短，成本全部来自「多一步」。

| 工具类型 | 占比 | 说明 |
| --- | --- | --- |
| 等待消息 | 最高，约 1/3 | 返回内容短；成本在「每调一次就多一步全量请求」 |
| 发送消息 | 次高 | 必要成本 |
| 已读 / 贴纸 / 最近消息 / 日记 / 未读 | 零星 | 单次收益低、步数固定 |
| **短记忆写入** | **0** | 工具常驻但从未被调用（见 Q5） |

**工具结果体积分布（结论，不列明细表）**：

- 单条结果的中位数约 450 字符、p90 约 800 字符；最长的一条约 1.5 万字符。
- **超过 4,000 字符的只有个位数条；超过 20,000 字符的一条也没有。**
- 累计十几万字符 —— 这个数字是**数百条之和**，不是任何单条的长度。曾把「某工具累计 5 万字符」误读成「该工具单条太长」，实际单条上限不到 900。

结论：工具结果**单条都不长**，真正的体积是「条数 × 每步重放」。任何按单条长度设计的剪枝阈值（`thresholdChars: 50000`）在这类负载上都不会触发一次 —— **从未触发不是配置错误，而是负载里没有长结果。**

**现有守门及其盲区**：

```js
{ enabled: true, cacheRateMin: 0.95, dailyInputMax: 150_000_000, topShareMin: 0.5 }
```

三个口径：缓存命中率、单日输入总量、单会话占比；输出只是一行日报/告警文字。日累计输入通常只有红线的一个零头（量级上差 3–5 倍以上）—— 也就是说：**它只在异常爆发时响，无法在上下文缓慢增长期给出任何早期信号，也不做任何拦截。**

**这是 Q1 最直接的证据**：钱不是被「话多」烧掉的，是被「一个永不轮换的会话」烧掉的；单日花费波动可以差一个数量级，而同一天的消息量并没有相应变化。

### 3.4 诊断（Q1–Q6）

| # | 诊断 | 证据 |
| --- | --- | --- |
| Q1 | **上下文无上界，单步成本线性增长** | 会话只会在重置 / 模式变更 / 丢失时退役；记录中没有任何 compaction 事件；累计花费集中在单个未轮换会话 |
| Q2 | **静默轮为几个字符的决策支付整份上下文** | 静默轮每轮 1 步、输入与正常轮同量级、输出个位数 token |
| Q3 | **步数被等待类工具放大** | 等待类工具约占调用三分之一；极端轮次 20+ 步，单轮可达百万 token 量级 |
| Q4 | **剪枝器从未生效过一次** | 阈值 50,000 远大于最长单条（约 1.5 万）；**不是配置错，而是负载无长结果**，真正的体积在累积 |
| Q5 | **L1 短记忆层空转，但成本照付** | 短记忆写入工具调用次数为 0；其 schema 常驻（每步数百 token）；衰减逻辑每轮空跑；提示词仍在教它写 |
| Q6 | **现有守门管不到这个失效模式** | 没有「单会话上下文水位」口径；只有日累计超红线才报警，且不拦截 |

### 3.5 方案（O1–O7）

#### O1 · 上下文守门 + 会话交接轮换（核心，收益最大）

**纯函数模块**：

```js
export function evaluateContextBudget(steps, cfg) {
  // 调用方必须先按 sid 过滤、去重，并按真实事件时间/序号排序。
  // 不能取历史最大值：那会让会话在曾经越线后永久保持高水位。
  const latest = steps.at(-1);
  if (!latest) return { watermark: null, level: 'unknown', ...cfg };
  const watermark = latest.cacheHit + latest.cacheMiss;
  const level = watermark >= cfg.hardAt ? 'hard'
              : watermark >= cfg.softAt ? 'soft' : 'ok';
  return { watermark, level, softAt: cfg.softAt, hardAt: cfg.hardAt };
}
// 初始候选值 softAt = 60_000, hardAt = 120_000；上线前用观测分布校准
```

**唤醒入口行为**：

- `ok` → 正常运行。
- `soft` → 记录 `[budget] 上下文 62K（soft）`；可追加「优先合并工具调用、避免非必要等待」的轻量提示（不能替代工具侧硬限制）。
- `hard` → 置 `pendingHandoff = true`，**不在处理消息时立即换会话**，等安全交接点。
- `unknown` → 只记诊断日志，**不自动轮换**（避免日志缺失触发错误动作）。

**交接轮换五步**（候选条件：距最后一条相关消息 ≥5 分钟、距上次成功交接 ≥6 小时）：

```
① 在旧会话生成一次「不发送」的结构化交接：
   {"topics":[],"openLoops":[],"peopleChange":[],"mood":"","insideJokes":[]}
   约束：≤400 字；只记后续对话确实需要的内容；字段可为空；不得猜测缺失事实。
② 校验 JSON、长度、敏感信息与 schema 版本；无效结果不得覆盖最近一次有效交接。
③ 先写临时文件再原子替换交接文件（按会话 key 分文件）；保留最近 3 份，记录生成时间、
   来源 session、schema 版本、成功/失败状态。
④ 只有交接持久化成功后才 retireSession(key)；交接失败则保留旧会话并重试/告警。
   禁止先退役再写文件。
⑤ 下次唤醒新建 session，在 memoryLine 之后注入 handoffLine（初始预算 600 tokens）。
```

**参数依据**：60K / 120K 是**初始候选阈值**，不是已证明的最优值；各项预算混用字符与 token，不能直接相加；上线前用真实单步输入分布校准。采用绝对阈值便于解释与告警；未来换窗口不同的模型再加 `softRatio/hardRatio`，但**必须同时设绝对上限**。

**风险与缓解**：

| 风险 | 缓解 |
| --- | --- |
| 交接丢细节，手感断裂 | 交接只放「必须知道的」；原文由 `wake-history`（12 条）+ L2 档案兜底；轮换后 24h 人工抽查 3 个切换点 |
| 交接 turn 本身要一次全量请求 | 只在水位超 hard + 安静期 + 6h 冷却时触发，约每 2–3 天一次 |
| 前缀缓存重建，首轮全额未命中 | 已计入预期（新会话首轮全额未命中，约等于一段固定系统提示词的额外成本） |
| 轮换期间丢消息 | 交接在安静期执行，新消息进可恢复队列，新会话继承 unread |

**验收**：单测覆盖空数据/重复行/重试/跨 session 混入/乱序/最新记录低于历史峰值；影子运行 ≥24h（只算不算）；小流量后首轮 `<60K`；7 天观察均值/中位数/P95；20 个交接点人工抽查；任何丢未回消息、人物错关联、隐私外泄即回滚。**回滚必须能恢复旧 session 映射**，不能只关开关却留下半完成退役状态。

**工作量**：1–2 天（含离线单测）。**收益 `[推算]`**：稳态单步降到数万 token 量级、日花费下降一个数量级，均为待验证目标，不得写成已实现。

#### O2 · 工具结果剪枝 —— 已否决（保留为反例）

**结论**：调 `tool-result-pruner` 阈值**不会省到钱**。这份负载里单条结果超过 4,000 字符的只有个位数条（最长一条约 1.5 万字符），把阈值从 50,000 降到 4,000 至多裁掉这几条，合计不到 2 万字符 ≈ 数千 token —— 相对数十万 token 的单步输入是 2% 量级的噪声，且最长那条通常是提示词快照，裁掉等于自伤。

**为什么前两版判错方向**：v1 看到「某工具累计 5 万字符」，推断「该工具返回太长」；v2 质疑了 pruner 语义，但没有质疑**收益前提**。逐条量体积后，前提不成立。

**真正的体积**：十几万字符来自**数百条结果的累积**，随历史全量重放、每步一次。这是 O1 的问题 —— pruner 按单条阈值工作，结构上无法处理「条数 × 轮数」。

**保留的验证动作**（1 小时，作为否定证据）：用固定样例（短/长/结构化列表/尾部关键字段）跑一次插件，确认 `thresholdChars` 是单条语义、头尾如何解释，把结论登记进未知项，然后关闭此项。

**方法论教训（值得推广到所有优化项）**：先质疑「这个机制作用的对象存在吗」，再验证「这个机制的语义」。语义验证通过而对象不存在，是零收益。

#### O3 · 等待步瘦身

**代码事实（决定只能怎么改）**：

1. **静默轮已经只有 1 步**（输出 3–4 token），没有可省的步数；可省的只有它那一步的全量上下文 —— 那是 O1 的活。
2. **步数成本集中在活跃轮**（中位数为个位数，极端轮次 20+）。每省掉一次 `wait` = 省掉一次整份上下文请求，这才是 O3 的收益单位。
3. **`mark_read` 有代码级拦截**：睡眠配置且 `preSleepWaitBlockedV2(st)` 为真时直接 400，错误原文：
   `还不能通过 qq_mark_read 直接回到潜水：还需等待约 N 分钟无新消息，或调用 qq_wait_for_messages(timeoutMs=300000) 完成一次沉睡前观察。`
   放行条件只有四种：唤醒配置是 active / `anyMessage`、`preSleepWaitEnabled === false`、`hasExplicitEndV2(st)`、已安静满 `preSleepWaitMs`（默认 300000）；另有 `preSleepWaitSatisfiedAt`（等待期间无人说话）或 `preSleepWaitObservedAt`（等待期间有人说话）已写入且其后无新消息也放行，这两个时间戳由 `wait` 的返回写入。
   → **「静默轮跳过观察直接收尾」不是提示词能解决的**，必须改判定口径；这也解释了 `preSleepLine` 那段提示词为何存在（绕不过拦截的安慰剂）。
4. **`throughSeq` 的上界**：要求 `throughSeq ≤ 已展示连续消息水位`，超过即 400；但**不传 `throughSeq` 时会走兼容路径清空全部 unread**。因此风险收窄为两条：(a) `throughSeq` 只保证「不超过已展示」，**已展示但未处理**的消息仍会被标已读；(b) 省略 `throughSeq` 会一次否掉整队未读。

**改动（分阶段）**：

1. `wait` 返回改为增量摘要：`本次新增 N 条` + 首尾各 2 条 + 明确游标/时间范围；保证可用 `qq_get_recent_messages` 补看。
2. 记录每轮 wait 次数与返回消息数；测试环境验证单轮上限候选值 2。
3. 只有确认游标、未读状态与处理顺序不变量后才启用上限；超限应**安全结束当前步骤并保留未处理消息**，不得只返回错误而丢失控制流。
4. **静默轮不强制观察**（新口径）：
   a. `preSleepWaitBlockedV2` 增加「本轮判定为静默、且本轮未发送任何消息」的放行分支，保留 `preSleepWaitEnabled` 一键回滚；
   b. `mark_read` 侧要求显式 `throughSeq`，拒绝省略路径；
   c. `throughSeq` 允许小于已展示水位（模型只确认它真正处理过的部分），日志记录 `markedCount` 与 `unreadCount` 的差；
   d. 观察「聊两句又潜水」是否回潮 —— 这正是该函数存在的目的，用灰度日志 + 人工抽查判定，不达标就回滚 a。

**验收**：至少 7 天观察 wait 次数、步数中位数/P95、未读积压、漏回；抽查 20 轮。**任何消息被错误标记已读即回滚**。收益 `[推算]`：步数中位下降、调用量 −20~30%，须与 O1 分开测量，避免把组合收益归因给单项。

#### O4 · 短记忆：自动化，或者删掉

**方案 A（有条件推荐）**：`activeTopics` 由交接 turn 顺带产出（`topics` 经 schema、去重、过期规则校验后写入「活跃话题」持久化结构）。**只有在确认没有外部调用者、旧提示词引用、控制台入口或用户工作流依赖后**，才删除 `qq_memory_append/query/remove/list` 四个工具；删除前提供兼容期/弃用日志。`memberImpressions` 并入 L2 需要字段映射、去重和回滚迁移，不可直接丢弃原数据。

**方案 B**：桥接侧规则抽取 —— 投喂摘要时从最近 30 条取「被重复提及的名词 / 被 @ 的人」upsert `activeTopics`。不依赖 O1，但规则抽取质量差。

**取舍**：A 更省（少 4 个工具 schema + 一段提示词），但把「记忆写入」绑死在轮换上（若关闭 O1，L1 就没有写入者 —— 可接受，因为 L1 本来空转）。

**验收**：轮换后 `activeTopics` 非空且与最近话题相关；提示词 token 数下降。

#### O5 · 档案抽取 backlog

**问题**：`sliceMaxMessages: 40` 意味着抽取只看最近 40 条。聊得快时，中段内容在被抽取前滑出窗口，**永久丢失**；`extractCooldownMs: 30min` 在积压时反而拖慢。

**改动**：

1. 保留 40 条作为单次上限；新增持久化游标/队列，按「尚未处理的消息区间」分片推进。
2. 每个分片成功抽取并写入档案后才提交游标；失败可重试，以消息 ID/区间保证幂等。
3. 先明确 backlog 保留上限与溢出策略。**默认不静默丢弃最旧未处理消息**；必须限流时记录被丢弃区间/条数/原因并告警。
4. 冷却自适应作为第二阶段：先记录 backlog 深度与抽取耗时，再验证 `pending < 30 → 30min`、`pending ≥ 30 → 10min`。
5. 质量门槛不变（`looksLikeBareLabel` / `scrubSensitive` / 6–160 字 / 必须带 evidence），继续保持独立学习会话。

**验收**：模拟失败/重启/重复执行/backlog 超限验证游标正确性；统计待处理数、最老消息年龄、成功/失败次数；抽查条目均有 evidence 且非空泛标签。

#### O6 · 摘要投喂可观测（约 2 小时）

L3 是「潜水也知道发生了什么」的唯一通路，但日志里**一条相关记录都没有** —— 无法区分「今天没群聊所以没触发」与「机制坏了」。

**改动**：3 个计数 + 3 条日志：入队 `[summary] 入队 n 条（待投喂 m 条）`、投喂 `已投喂 k 条`、作废 `silent 名额超时作废`。
**验收**：群聊恢复后 24h 内能量出这三个数。

#### O7 · 控制台补「上下文水位」列（约半天）

**改动**：「令牌与花费」页每行加一列 `上下文 = cacheHit + cacheMiss`，按 soft/hard 染色；守门新增第 4 口径 `contextWatermarkMax`（单会话水位阈值，默认 120K）。
**必须注意**：聚合必须 `filter(k === 'turn')`，否则虚高 100 倍。
**验收**：控制台单步上下文与探针一致；越线出现告警行。

### 3.6 明确不考虑（及理由）

1. **用向量检索替代 L2 档案**：现有档案是「具体事例 + evidence + 30 天半衰期 + 按类取 1 条」，质量高于 top-k 片段召回，且无额外延迟；跨会话语义回忆已由 L4 覆盖。引入检索会同时丢掉「时间衰减」与「证据约束」。
2. **每天定时 /reset**：会丢掉正在进行的玩笑、表情包语境、未回应的消息 —— 手感崩坏且用户可感知。必须用「安静期 + 交接」。
3. **缩短 `contextWindow`（现有 20 条原文）**：20 条是对话连续性的下限；该省的地方是「不该说的话」（O1/O3），不是「听懂对方」。

## 4. 两套方案的交叉影响（合并后新增的判断）

这 8 条是单看任何一份文档都得不到的，**是本文的主要增量**。

**X1 · 同一个病：无上界累积 + 无度量。**
表达层：规则只增不减、只有 `log()`，答不出「哪条最常触发 / 误伤多少」。成本层：历史只增不减、守门 150M 才告警。所以两边的第一优先级都应是「先量再改」，而不是加规则/调阈值。

**X2 · 两处「加计数器」是同一件事，应合并基建。**
表达层的出站计数（P0-1）与成本层的单步水位（O7）都应该是：写一行记录 → 按天聚合 → 只读 API → 控制台一列。建议一次做成同一套 stats 基建（同一落盘器、同一脱敏策略、同一保留期），避免两套日桶、两套清理逻辑。

**X3 · O1 完成后，成本主战场会转移到「固定提示词 + 工具 schema」。**
理由：轮换后稳态单步 = 系统提示词（固定部分 5–8K 字符 ≈ 4–6K tokens）+ 交接（600 tokens）+ 少量历史 + 工具结果。此时 P1-3 人格卡瘦身、工具面裁剪的收益占比**上升**；在 O1 之前，它们的收益被 264K 的历史体积完全掩盖，测不出来。
→ **顺序含义**：先 O1，再提示词瘦身，否则瘦身效果无法归因。
→ `[未知]`：全量工具 schema 的总体积尚未测量（已知 4 个记忆工具约 600–800 tokens/步）。若工具面占稳态大头，它会成为 O1 之后的下一个主要成本项，应先量再动。

**X4 · 两个长度阈值不一致（30 vs 40），中间有 10 字的「只靠劝」地带。**
预设要求「单条多数 ≤30 字」，长度闸门 `splitAbove=40`。30–40 字区间只有提示词约束、没有硬闸门。要么把闸门降到 30（增加拆条与误拆风险），要么承认闸门只是兜底、接受这段软区。**这是一个待决策项，本文不擅自定。**

**X5 · 两种「少说话」会叠加成「过静」，必须合并观测。**
静默轮（模型判 `[SILENT]`）+ 群聊 `fallback-skip`（洗空丢弃）都在减少输出，各自看都是「省成本 / 更自然」。合并后可能变成「机器人不怎么说话了」，而两份文档各自的指标都显示「一切正常」。
→ 需要统一指标：**无输出轮占比 =（静默轮 + 群聊 fallback-skip）/ 总轮**，并对「连续 N 轮无输出」设告警。这是唯一能发现「两个正确改动叠加成错误」的指标。

**X6 · 采样温度与过滤器耦合，盲评必须同时报告过滤统计。**
T=1.15 + penalties 提高多样性，也提高触发过滤/删空的概率。P1-2 的盲评若只报「自然度分」，可能把「更常被洗短」误判成「更自然」。
→ 盲评报告必须并列：删空率、规则命中率、平均删减字数、平均最终句长。
→ 注意：15 条固定样本直接喂 `deslopChatText`，与温度无关，**不能用来验证采样参数**。

**X7 · 两个单点都缺 fail-open。**
采样代理 8790 挂 → QQ 完全不回话（fail-closed 到沉默）；交接写文件失败若先退役 → 会话上下文全丢。两处的共同要求是：**故障时回落到原行为**（直连模型 / 保留旧会话），而不是回落到「不说话」或「清空」。
→ 建议把这条写成所有新组件的硬性设计规则，并各配一个失败注入测试。

**X8 · 归因顺序：O1 会污染其后所有指标。**
轮换改变单步输入、缓存命中与成本分布。因此：P1-2 采样 A/B 先离线做（固定上下文，不受轮换影响）；P1-1/P1-3 的线上效果观察放到 O1 稳定之后；O1 的验收也不该混入提示词改动。**一次只让一个结构变量变，否则 7 天报告全是混合归因。**

## 6. 统一评估方法

### 6.1 三层验证（每层有通过条件，不能跳级）

| 层 | 做什么 | 通过条件 | 现状 |
| --- | --- | --- | --- |
| T1 契约/单测 | 现有 8 个脚本 + 每个新模块的新脚本 | exit 0，且断言覆盖幂等与不误伤 | 表达层已覆盖；记忆层 O1/O5 尚无脚本 |
| T2 离线质量 | 固定回归集 + 隐藏版本信息的人工盲评 | 5 维指标不劣于基线 | **没有**，这是当前最大缺口 |
| T3 灰度线上 | 7 天指标 + 人工抽查 | 成本降且质量不降 | 未开始 |

**现有 8 个脚本守的是「实现没坏」，不守「改动是否真的更好」** —— 后者只能靠 T2，而 T2 还没有。

### 6.2 五维指标（每次规则或提示词变更必看）

| 维度 | 推荐度量 | 说明 |
| --- | --- | --- |
| 自然度 | 隐藏版本信息的人工盲评 | 评价是否符合对应场景，而非越短越好 |
| 语义保真 | 关键事实、数字、否定、专有名词保留率 | 清洗前后逐项核对 |
| 误伤率 | 被修改文本中经复核认为不应修改的比例 | 需定义抽样方法与复核标准 |
| 模板残留 | 固定测试集中的模板表达出现频率 | 只作辅助指标，不能单独代表自然度 |
| 系统稳定性 | 延迟、异常率、回退率、发送失败率 | 检查优化是否引入系统风险 |

成本层追加四维：**单步水位 / 步数 / 静默轮占比 / 日花费**（并区分峰谷）。

固定测试集，并为每次改动保留：版本号、配置、运行命令、原始结果。**只有相同测试条件下的对照，才能判断变化来自本次修改。**

### 6.3 灰度报告模板（两份来源的合并版）

必须包含：
- 版本、开关、阈值、观测时间范围；
- 样本量：会话数、轮数、请求/step 数、静默轮数；
- 单步输入 token 的均值/中位数/P95/最大值；
- 每日花费、峰谷分布、缓存命中率；
- O1 触发次数、实际交接次数、交接 turn 的 token 与成本；
- 表达层：Top5 命中规则、删空（skip/keep-raw/heavy）次数、平均删减字数、无输出轮占比；
- 漏回/重复回复、交接后话题断裂、档案错误或敏感内容问题；
- 结果状态：**通过 / 失败 / 证据不足**，并注明回滚决定。

## 8. 不要做清单（合并版）

- ❌ 不用 LLM 对每条消息做自动二次改写：除非离线评估证明收益，否则增加延迟、成本和语义漂移。
- ❌ 不把 `fallback` 换成随机句：随机回退会形成新的固定口头禅，也让回应与上下文脱节。
- ❌ 不追求「规则清零 AI 词」：真人也会说「慢慢来」「加油」，删干净反而更不自然。
- ❌ 不把短句、漏回、延迟或错字当作真人感的唯一来源；不为风格牺牲准确性、可理解性或诚实性。
- ❌ 不在未测量误伤率前批量启用新删除规则（P0-5 因此只记 flag）。
- ❌ 不把计划、预期或示例结果写成已验证结果。
- ❌ 不用向量检索替代 L2 档案（会丢时间衰减与证据约束）。
- ❌ 不每天定时 /reset（丢玩笑语境与未回消息，手感崩坏）。
- ❌ 不缩短 `contextWindow`（20 条是连贯性下限；该省的是「不该说的话」）。
- ❌ 不靠调 `tool-result-pruner` 阈值省钱（无对象可裁，已验证）。
- ❌ 不用人为随机延迟掩盖系统问题，也不把「看起来像真人」当伪造身份的理由。
- ❌ 不为风格处理无限扩大个人数据收集（昵称来源只限必要范围）。

## 附录 B · 关键契约（移植与审查用）

**B1 `deslopChatText(text, opts) → { text, hits }`**
纯函数、零依赖、确定性。平台差异只在 Markdown 规则（渲染 Markdown 的平台关掉 `md-*`）。移植时必须补：修改原因、语义保真测试、空结果处理。

**B2 `deslopOutgoing(key, raw) → string`**
唯一强制点。行为：告警前缀跳过 → 清洗 → 六档兜底决策 → 记统计 → 返回最终文本（空串 = 不发）。

**B3 `planLengthSplit(text, cfg) → { action, parts, reason }`**
`action ∈ {none, split, warn, skip}`；`split` 时 `parts.length ∈ [2, maxParts]`。字段名为本文约定，以实现为准。

**B4 `humanGapMs(chars) = clamp(300 + 45 × chars, 600, 4000) × U(0.8, 1.2)`**

**B5 `ensureSession(key)`**：只有代际不匹配、DSH 侧不存在、`retireSession()` 显式调用三种出口；正常路径永远复用。

**B6 `evaluateContextBudget(steps, cfg) → { watermark, level, softAt, hardAt }`**
`level ∈ {ok, soft, hard, unknown}`；`unknown` 永不触发自动动作。

**B7 交接 JSON schema v1（建议；字段按 O1 第 ②③ 步的校验与元数据要求组织）**

```json
{ "schema": 1, "topics": [], "openLoops": [], "peopleChange": [],
  "mood": "", "insideJokes": [], "generatedAt": 0, "sourceSession": "session-<uuid>",
  "status": "ok|failed" }
```

**B8 关键日志字符串（排障靠它们）**

```

```

**B9 数据落盘**（文件名为本文约定，实现时按平台替换载体）

## 附录 C · 脱敏与可移植说明

### C1 本文的数据处理原则

| 处理对象 | 本文的做法 |
| --- | --- |
| 账号 / 群号 / 会话标识 | 一律不出现，以 `<账号>`、`<群号>`、`session-<id>` 之类占位 |
| 聊天内容原文 | 不引用（只保留公开的 AI 腔示例句与机器人自身风格样例） |
| 昵称 / 群名缓存 | 只描述机制与上限，不列任何真实昵称 |
| 运营数据（轮次、花费金额、调用计数） | 不出现具体值；只保留**量级与比例**，用于说明结构 |
| 实现细节（文件路径、行号、测试断言数、实施日期） | 不出现；只保留函数名、配置键与参数值这类**方案必需**的信息 |

**保留项及其理由**：模型名与公开计价（公开信息）、参数阈值与配置键（实施必需）、功能名称与函数名（评审必需）。

### C2 移植只需要三个钩子（与平台无关）

1. **每轮提示词**：一段「核心必看」（≤400 字）+ 按场景选 1~2 段 + 2~4 条真人样例。
2. **发送前函数**：`deslopChatText(text, opts)` 纯函数，可直接搬运。
3. **消息节奏**：条数上限、间隔按字数、长停顿概率、漏看/不回的概率。

需要按平台重写的只有三件事：**哪些字符算「告警前缀」、单条字数上限、是否渲染 Markdown**。
